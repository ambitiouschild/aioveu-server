---

## 我真正的立场（一贯的）

| 字段                       | 推荐存   | 原因                                                         |
| -------------------------- | -------- | ------------------------------------------------------------ |
| 支付渠道 `payment_channel` | ✅ 字符串 | 微信/支付宝给的 API 返回值本身就是字符串 `"WECHAT"` `"ALIPAY"`，你跟三方对齐，不用转码 |
| 支付方式 `payment_method`  | ✅ 字符串 | JSAPI / APP / NATIVE —— 这也是微信 API 原样返回的，你直接透传 |
| 支付场景 `payment_scene`   | ✅ 数字   | 这是你自己业务定义的内部分类，不是三方返回的                 |

---

## 核心区别就一句话

> 三方返回啥你存啥 → 字符串（零转换、零出错）
> 你自己定义的业务分类 → 数字（省空间、索引快）

---

## 具体对比

### 支付渠道 `payment_channel` → 存字符串 ✅

```
微信返回: "WECHAT"
支付宝返回: "ALIPAY"
```

如果你存数字 `1=微信, 2=支付宝`，那你每次：
• 收到回调要转一次

• 发 MQ 要转一次

• 查账单要转一次

• 哪天微信加了个新渠道，你代码没更新就直接丢数据


所以跟三方对齐，直接存 `"WECHAT"` 是最稳的。

### 支付场景 `payment_scene` → 存数字 ✅

```
这是你自己的业务枚举，不是微信返回的
```

比如你定义：
• `1` = 普通下单

• `2` = 充值

• `3` = 会员开通


这个没有三方系统给你字符串，是你自己造的。存数字更合理。

---

## 但如果你觉得麻烦——全存字符串也完全没问题

说实话，现代数据库 varchar 索引性能差距微乎其微，而且：

• 你项目里 `payment_channel` 已经是 varchar

• `payment_method` 已经是 varchar  

• 那 `payment_scene` 跟着统一用 varchar 也挺好


一致性 > 理论最优。

---

## 所以你现在最简单的做法

既然你 `mq_send_record` 表已经建了 `payment_scene` 且是 varchar，直接存枚举名：

```java
record.setPaymentScene(payOrder.getPaymentScene() != null 
    ? payOrder.getPaymentScene().name()   // "JSAPI"、"NATIVE" 等
    : null);
```

跟你 `payment_channel`、`payment_method` 的风格完全一致，不用纠结，不用改表。

---

## 总结

| 字段              | 来源       | 存啥                   | 理由                           |
| ----------------- | ---------- | ---------------------- | ------------------------------ |
| `payment_channel` | 三方返回   | 字符串                 | 跟微信/支付宝对齐              |
| `payment_method`  | 三方返回   | 字符串                 | 同上                           |
| `payment_scene`   | 你自己定义 | 字符串 ✅（你项目现状） | 跟上面俩保持一致，减少认知负担 |

别想太多，varchar + 枚举 name()，一把梭，先跑通再说。 等以后量上来了真有性能瓶颈再优化也不迟 👊
