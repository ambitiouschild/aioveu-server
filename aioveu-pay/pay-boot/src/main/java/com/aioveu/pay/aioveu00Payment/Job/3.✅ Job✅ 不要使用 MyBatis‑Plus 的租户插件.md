## 一、为什么“Job 不要用 MP 租户插件”？

不是因为 MP 不好  
而是因为 语义从根本上不兼容

### ✅ Job 的本质是什么？

> Job = 平台视角、系统级行为、跨租户、无人值守、周期性

### ❌ MP 租户插件的本质是什么？

> 自动、隐式、强制、不可见地给 SQL 加 `tenant_id`

### 👉 两者放在一起，只有三种结局：

| 结局        | 结果               |
| ----------- | ------------------ |
| 返回 null   | NPE                |
| 返回 0L     | 查错数据           |
| ignoreTable | 逻辑爆炸、难以维护 |

你现在已经把这三条路都踩了一遍。

## 二、你现在的“混乱感”，本质是这句话

> “我在用一个为『用户请求』设计的插件，去跑『系统任务』”

这不是你用错了  
这是 模型错配

就像你不会用：
• 事务注解去跑批处理

• 登录拦截器去跑定时任务

• 权限框架去跑运维脚本


👉 租户插件也一样

## 三、✅ 正确的认知模型（你现在已经摸到边了）

### ✅ 多租户系统 ≠ 所有代码都多租户

而是：

```
┌────────────────────────────┐
│        用户请求路径        │
│  Controller → Service      │
│  → Mapper → MP 租户插件   │
│  ✅ 自动、透明、安全       │
└────────────────────────────┘

┌────────────────────────────┐
│        系统 Job 路径       │
│  Job → Service → Mapper    │
│  ❌ 不进租户插件           │
│  ✅ 显式、可控、全量       │
└────────────────────────────┘
```

👉 Job 不是“多租户的一部分”
👉 Job 是“站在多租户外面”的东西

## 四、✅ Job 不要 MP 租户插件，那用什么？

### ✅ 正确姿势只有一句话：

> Job 里：关掉插件，手写 SQL / Wrapper，不碰 `TenantContextHolder`

### ✅ 示例（标准写法）

```java
@Scheduled(cron = "0 */5 * * * ?")
public void reconcile() {
    // ✅ 关闭租户插件
    InterceptorIgnoreHelper.handle(
        IgnoreStrategy.builder().tenantLine(true).build()
    );

    try {
        // ✅ 全量查，不关心租户
        payOrderMapper.selectList(
            new QueryWrapper<PayOrder>()
                .lt("create_time", LocalDateTime.now().minusMinutes(30))
        );
    } finally {
        InterceptorIgnoreHelper.clearIgnoreStrategy();
    }
}
```

✅ 不设置租户  
✅ 不判断 JobContext  
✅ 不返回 null / 0L  
✅ 不依赖 ignoreTable

## 五、✅ 更进一步：Job 甚至不该“感知”多租户
