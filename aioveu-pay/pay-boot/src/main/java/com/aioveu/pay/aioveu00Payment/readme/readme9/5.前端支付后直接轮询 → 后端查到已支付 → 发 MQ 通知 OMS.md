从你之前的日志和代码来看：

| 步骤                     | 发生了什么                                                   |

所以你现在的问题是：微信回调进来 → 更新 DB 失败 → 前端永远轮询不到已支付状态。

## 那 MQ 在哪里？

正常设计有两种模式：

### 模式 A：回调里直接发 MQ（常见）

```java
// PayOrderSuccessHandlerServiceImpl.handlePaySuccess()
public void handlePaySuccess(String paymentNo) {
    // 1. 更新 pay_order 状态
    payOrderService.updateById(payOrder);  // ← 你现在这步炸了
    
    // 2. 发 MQ 通知 OMS 发货/改订单状态
    rabbitTemplate.convertAndSend("order.exchange", "order.paid", 
        new OrderPaidEvent(payOrder.getOrderSn()));
}
```

### 模式 B：轮询触发 + 发 MQ

```java
// PaymentServiceImpl.queryPaymentStatusByPaymentNo()
// 前端轮询时，如果发现刚变成"已支付"，顺便发 MQ
if (status == PAID) {
    rabbitTemplate.convertAndSend("order.exchange", "order.paid", event);
}
```

从你之前的 yml 配置看，RabbitMQ 是配了的：

```yaml
spring:
  rabbitmq:
    host: ${rabbitmq.host}
    listener:
      simple:
        acknowledge-mode: manual
```

所以 MQ 肯定在用。大概率是模式 A（回调直接发）。

## 你现在的状态总结

```
✅ 微信回调能进来（/wxpay/notify 接口能收到）
✅ 回调里查到了支付成功
❌ handlePaySuccess() 里 updateById 炸了（version=null）
❌ pay_order 没更新成"已支付"
❌ 前端轮询永远拿到"未支付"
❌ MQ 永远没发出去
```

你只要把 `handlePaySuccess` 里 update 之前先 `getById` 查出完整 entity（带 version），整个链路就通了：

```
微信回调 → 更新 pay_order ✅ → 发 MQ ✅ → OMS 接单 ✅ → 前端轮询到已支付 ✅
```

## 顺便说一下"前端轮询"这个设计

你可能会想：能不能不用轮询，改成 WebSocket / SSE 推送？

| 方案                    | 优点                 | 缺点                          |
| ----------------------- | -------------------- | ----------------------------- |
| 前端轮询（你现在用的）  | 简单、可靠、不怕断连 | 延迟 2~4 秒、多一次 HTTP 开销 |
| 微信回调后直接 redirect | 体验最好             | 小程序里不好做                |
| WebSocket 推送          | 实时                 | 要多维护连接、断线重连复杂    |

轮询对小商户/中小体量完全够用，不用急着改。先把乐观锁那个 bug 修了，支付流程就跑通了。
