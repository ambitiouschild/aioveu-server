## 二、为什么“参数驱动”让人心里发虚？

### 1️⃣ 单体时代给你洗了脑

以前你写的是：

```java
@GetMapping("/list")
public List<Order> list() {
    return mapper.selectList(null); // ✅ MP 自动拼 tenant_id
}
```

✅ 一行
✅ 不脏手
✅ 看起来“高级”

现在你要写：

```java
public List<Order> list(Long tenantId) {
    return mapper.selectByTenant(tenantId);
}
```

❌ 多一个参数
❌ SQL 要手写
❌ “我怎么退化了？”

👉 你不是怕啰嗦
👉 你是怕“失去框架保护”

---

### 2️⃣ “啰嗦”在心理上 = “低级”

我们潜意识里会觉得：

• 框架自动 → 高级

• 手写参数 → 初级

• DSL → 优雅

• if / param → 土


但分布式系统里，这个价值观完全颠倒：

| 认知 | 单体   | 分布式 |
| ---- | ------ | ------ |
| 自动 | ✅ 优雅 | ❌ 隐患 |
| 显式 | ❌ 啰嗦 | ✅ 正确 |
| 隐式 | ✅ 省事 | ❌ 事故 |
| 参数 | ❌ 低级 | ✅ 专业 |

---

### 3️⃣ 你舍不得的，其实是“确定性幻觉”

MP + ThreadLocal 给你一种幻觉：

> “我不用管租户，它总会在那儿。”

Feign 一调用，幻觉破灭。

但承认“要自己传参数”，等于承认：

> “没有魔法了，我要自己负责。”

👉 这不是啰嗦
👉 这是成长痛

---

## 三、一个很重要的“认知翻转”

你可以试着把这句话，换一种说法：

> ❌ “参数驱动太啰嗦了”
>
> ✅ “参数驱动是我主动选择的显式契约”

再换一句：

> ❌ “我退步了，要手写 SQL”
>
> ✅ “我升级了，我在定义系统边界”

## 四、为什么“啰嗦”反而是好事？

### ✅ 1️⃣ 啰嗦 = 可审查

```java
getAuthInfo(username, tenantId)
```

• ✅ 谁调用一目了然

• ✅ 单测直接传参

• ✅ 缓存 key 天然清晰


---

### ✅ 2️⃣ 啰嗦 = 不靠记忆

半年后你回来看：

• ❌ “这个接口靠哪个 Filter 塞 tenantId 来着？”

• ✅ “哦，参数里写着”


---

### ✅ 3️⃣ 啰嗦 = 不连锁

改一个 Filter：
• ❌ 影响 20 个接口

• ✅ 改一个参数：只影响调用方


---

这不是啰嗦
👉 这是职业尊严
