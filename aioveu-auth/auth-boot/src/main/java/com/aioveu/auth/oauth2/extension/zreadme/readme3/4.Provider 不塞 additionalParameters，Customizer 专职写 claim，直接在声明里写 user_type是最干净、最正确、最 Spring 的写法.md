## 二、为什么“直接在 Customizer 里写”是最优解

### 1️⃣ 职责单一（架构干净）

| 组件                                        | 该干的事                           |
| ------------------------------------------- | ---------------------------------- |
| `AuthenticationProvider`                    | 认证、加载主体、存 `Authorization` |
| `OAuth2TokenCustomizer<JwtEncodingContext>` | 专门往 JWT 里写 claim              |

你现在的分工：

```text
Provider:
  → principal 识别
  → token_version 校验
  → Authorization.attribute(user_type)   // 给内部用

Customizer:
  → claims.claim("user_type", ...)        // 给外部 JWT
```

✅ 不抢活、不越层。

---

### 2️⃣ `additionalParameters` 本来就不是给 JWT claim 用的

你之前踩的那个坑：

```java
DefaultOAuth2TokenContext.Builder
    .additionalParameters(...) // ❌ 不存在
```

本质原因：
• `additionalParameters` 是 授权请求参数

• JWT claim 只能从：

  • `JwtEncodingContext.getClaims().claim()` ✅

  • 或 `Authorization.attribute` + Customizer 读取 ✅


你现在的写法：

```java
addClaim(claims, JwtClaimConstants.Token.USER_TYPE, "USER");
addClaim(claims, JwtClaimConstants.Token.USER_TYPE, "MEMBER");
```

👉 是唯一标准答案。

---

### 3️⃣ 资源服务器侧最省事

以后你资源服务器里：

```java
String userType = jwt.getClaimAsString("user_type");
```

不用查 Redis、不用反序列化 Authorization、不用猜主体类型。

```
   ├─ principalName

   ↓

{

  "token_version": 3,
  "tenant_id": 1
}
   ↓
Resource Server（直接认人）
```
