## 二、先回答你：技术上“怎么触发 MP”

如果你**铁了心**要在 `auth → tenant`的 Feign 调用里让 MP 生效，**只有两条路**：

------

### ✅ 路线 A（勉强可行，但不优雅）

#### 在 Feign 调用时，把 tenantId 带给 tenant 服务

**Feign Interceptor：**

```
requestTemplate.header("X-Tenant-Id", TenantContextHolder.getTenantId().toString());
```

**tenant 的 Filter：**

```
String tenantId = request.getHeader("X-Tenant-Id");
TenantContextHolder.setTenantId(Long.valueOf(tenantId));
```

✅ MP 会生效

❌ 但你引入了：

- 

  Header 信任

- 

  Filter 逻辑分支

- 

  隐式依赖

- 

  调试地狱

👉 **这是“为了 MP 而 MP”**

------

### ✅ 路线 B（更不推荐）

让 Feign 调用带上 JWT，走完整 Security 链路：

```
Authorization: Bearer xxx
```

❌ 认证接口用 JWT

❌ token 可能过期

❌ 语义混乱

❌ 审计困难

👉 **这是架构事故预备队**

------

## 三、为什么“参数驱动”是唯一正确解？

### ✅ 1️⃣ 语义正确

| 场景         | 租户来源          |
| ------------ | ----------------- |
| 用户请求     | JWT / ThreadLocal |
| 认证内部调用 | **方法参数**      |

你这个 Feign 接口的本质是：

> **“系统查询某个租户下的用户凭证”**

不是：

> “用户发起的请求”

------

### ✅ 2️⃣ 可预测性

参数驱动：

```
WHERE tenant_id = #{tenantId}
```

✅ SQL 一眼可审

✅ 单测可写

✅ 缓存 key 清晰

✅ Feign 调用 100% 稳定

MP 隐式驱动：

```
WHERE tenant_id = ?
-- ? 从哪里来？谁 set 的？什么时候 set 的？
```

❌ 调试靠运气

------

### ✅ 3️⃣ 生命周期清晰

| 阶段   | 参数驱动 | MP 隐式    |
| ------ | -------- | ---------- |
| 编译期 | ✅ 可见   | ❌ 不可见   |
| 运行期 | ✅ 确定   | ❌ 依赖线程 |
| Feign  | ✅ 天然   | ❌ 强扭     |
| 缓存   | ✅ 明确   | ❌ 易串     |

------

### ✅ 4️⃣ 你现在已经站在“正确的一边”

你之前已经验证过：

- 

  MP 在 tenant 里 **不可控**

- 

  ThreadLocal **跨服务不存在**

- 

  白名单 **必须 skip**

- 

  缓存 **按 tenantId 隔离**

👉 **参数驱动是唯一能解释这一切的模型**
