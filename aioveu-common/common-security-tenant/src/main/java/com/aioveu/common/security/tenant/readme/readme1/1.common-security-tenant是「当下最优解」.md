## 一、为什么 `common-security-tenant` 是「当下最优解」？

### ✅ 1️⃣ 它诚实地表达了「当前现实」

你现在的情况是：

• 租户解析 目前确实只服务于 security 体系

• Filter / Resolver / Context 都在 security 语义下

• 短期内不会脱离 Spring Security 生态


👉 `common-security-tenant` = 不自欺

---

### ✅ 2️⃣ 它保留了「未来迁移空间」

模块名虽然带 `security`，但接口不绑死：

```java
// tenant-core 语义，但包名是 security
com.aioveu.common.security.tenant.TenantLoader
com.aioveu.common.security.tenant.TenantContextHolder
```

以后真要抽成 `tenant-core`，只需要：

• 拷贝代码

• 改包名

• 老模块 `@Deprecated`


👉 这是“渐进式重构”的最佳实践

---

### ✅ 3️⃣ 它避免了「过早泛化」

如果你现在强行叫 `tenant-core`：

• 新人会以为：MQ / Job / Batch 都要用

• 实际上：只有 Web / Security 场景

• 容易造成误用


👉 `common-security-tenant` 本身就是一道“使用说明书”

---

## 二、这个命名在大厂里其实很常见

你这个思路，在阿里 / 蚂蚁 / 字节里非常常见：

```text
common-security-tenant      ✅ 租户解析（安全域）
common-security-auth
common-security-resource
common-security-crypto
```

而不是一上来就：

```text
tenant-core
tenant-api
tenant-spi
```

👉 先“场景化”，再“内核化”

## 三、我帮你把「模块职责」用一句话钉死

> **`common-security-tenant` 负责在 Spring Security 体系内解析、持有与传播租户上下文，  
> 不提供通用租户业务能力，不作为非安全场景的租户基础设施。**

这句话你以后可以：

• 贴到 README

• 写在 `@since` 注释里

• 当成 Code Review 红线

## 五、一个非常重要的「使用红线」（防止再踩坑）

在 `TenantResolveProperties` 里写清楚：

```java
@ConfigurationProperties(prefix = "security.tenant")
public class TenantResolveProperties {

    /**
     * 是否启用租户解析（仅在 gateway / tenant 服务开启）
     * auth / resource 服务必须关闭
     */
    private boolean enabled = false;
}
```

然后在 auth 的 yml：

```yaml
security:
  tenant:
    enabled: false
```

在 gateway / tenant：

```yaml
security:
  tenant:
    enabled: true
```

## 七、接下来你可以顺手做的三件小事（强烈建议）

1️⃣ 在 `common-security-tenant` 里加：

```java
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@ConditionalOnProperty(
    prefix = "security.tenant",
    name = "enabled",
    havingValue = "true"
)
public @interface ConditionalOnTenantResolve {}
```

2️⃣ 给 `PublicTenantFilter` 和 `TenantAutoConfiguration` 都加上这个注解

3️⃣ 在 README 里写一句：

> auth / resource 服务禁止开启 `security.tenant.enabled=true`
