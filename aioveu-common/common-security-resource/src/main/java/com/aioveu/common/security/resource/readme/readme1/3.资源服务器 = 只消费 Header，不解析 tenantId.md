## ✅ 一句话结论（先拍板）

> 是的，`PublicTenantFilter` 在“资源服务器”里：
>
> ✅ 可以存在（因为 jar 里有）
> ❌ 但绝对不能干活（必须 `enabled=false`）
>
> 👉 资源服务器 = 只消费 Header，不解析 tenantId

你之前在资源服务器里用，不是“用错了”，而是“开错了开关”。

## 二、为什么资源服务器“可以有 Filter，但不能解析”？

### ✅ 1️⃣ Filter 是怎么进来的？

因为你有这个依赖：

```xml
<dependency>
    <groupId>com.aioveu</groupId>
    <artifactId>common-security-tenant</artifactId>
</dependency>
```

👉 Spring Boot 自动扫描
👉 `PublicTenantFilter` 必然被注册
👉 这不是你控制的，是自动装配的结果

---

### ✅ 2️⃣ 那资源服务器为什么不能解析？

因为资源服务器的正确语义是：

| 行为                     | 资源服务器 |
| ------------------------ | ---------- |
| 解析 tenantId            | ❌          |
| 查数据库                 | ❌          |
| 调 Feign                 | ❌          |
| 校验 JWT                 | ✅          |
| 从 Header 拿 X-Tenant-Id | ✅          |
| 传给 MyBatis / Service   | ✅          |

👉 解析 = 权威行为
👉 资源服务器 = 信任网关 / auth

---

## 三、你之前“在资源服务器里用”到底发生了什么？

### ❌ 当时的场景（大概率）

```yaml
security:
  tenant:
    enabled: true   # ❌ 开着
```

于是：

```text
请求 → resource
↓
PublicTenantFilter.doFilter()
↓
tenantLoader == null
↓
💥 NPE
```

👉 不是 Filter 不该存在
👉 是你让它“干了不该干的活”

## 四、✅ 正确的资源服务器用法（现在这套架构）

### ✅ 1️⃣ 依赖可以留

```xml
<dependency>
    <groupId>com.aioveu</groupId>
    <artifactId>common-security-tenant</artifactId>
</dependency>
```

✅ Filter 在 classpath 里 ✅ 正常

---

### ✅ 2️⃣ 但开关必须关（最关键）

```yaml
security:
  tenant:
    enabled: false
```

### ✅ 3️⃣ Filter 的真实行为

```java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    // enabled = false → shouldNotFilter = true
    return !tenantProperties.isEnabled();
}
```

👉 Filter 被加载
👉 但 doFilterInternal 永远不执行
👉 零开销、零风险

## 五、一个非常重要的“认知升级”

> ❌ 旧认知：  
> “资源服务器里不能有 PublicTenantFilter”

> ✅ 新认知：

| 方案                      | 问题               |

| 条件装配 Filter           | 模块边界混乱       |
| ✅ enabled 开关            | 统一入口、语义清晰 |

👉 你这套是“平台级方案”

## 六、一个“反直觉但正确”的事实

你现在的资源服务器：

```text
✅ 有 PublicTenantFilter.class
✅ 有 TenantContextHolder.class
✅ 有 TenantLoader 接口
❌ 没有 TenantLoader Bean
❌ 不执行解析逻辑
```

👉 这是“接口存在，实现不存在”的典型 IoC 用法
