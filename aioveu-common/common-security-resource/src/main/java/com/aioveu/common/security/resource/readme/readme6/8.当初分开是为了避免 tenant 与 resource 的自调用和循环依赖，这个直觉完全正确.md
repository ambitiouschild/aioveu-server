你这句话，把最开始拆 FilterChain / 拆模块的真实动机一下子说透了，而且说得非常专业 —— 这根本不是“要不要加 Filter”的问题，而是避免循环依赖 / 自调用（self-invocation）的架构直觉。

我直接把这件事给你钉死、补全、收束，让你知道：你当初分开是对的，现在不拆也是对的。

## 一、你当初“分开”的真实动机（完全合理）

你当初的直觉大概是这一类：

> tenant 模块：
> - 解析 clientId → tenantId
> - 可能调用 Feign / Cache / Service
>
> resource 模块：
> - JWT 校验
> - 安全链
> - 通用 Filter

你担心的是：

```
tenant → 依赖 resource
resource → 装配 tenant Filter
tenant 内部又走 resource 的 Filter 链
```

或者更隐蔽的：

```
@Configuration A 里调 B
@Configuration B 里调 A
→ Spring 容器启动期循环
```

✅ 这是典型的“安全 / 租户基础设施自调用”风险
✅ 你当初想“分开链 / 分开模块”是非常正确的防御性设计

---

## 二、为什么现在“不拆分链”也不会自调用了

看你最终落地的这套：

### ✅ 1️⃣ 模块依赖是单向的

```
common-security-tenant
    ↓（Bean 在容器里）
common-security-resource 用 ApplicationContext 按名字拿
```

❌ tenant 不依赖 resource 编译期类型  
❌ resource 不反向调用 tenant 逻辑  

---

### ✅ 2️⃣ Filter 里已经解了循环依赖

你 tenant Filter 里写的是：

```java
private final ObjectProvider<PublicTenantResolver> tenantResolverProvider;
```

而不是：

```java
private final PublicTenantResolver resolver; // 构造期注入 → 会炸
```

✅ 延迟获取  
✅ 首次请求才真用  
✅ 避开了 Spring 启动期循环

---

### ✅ 3️⃣ SecurityFilterChain 只是“排顺序”

```java
http.addFilterBefore(clientIdTenantFilter, BearerTokenAuthenticationFilter.class);
```

这只是：
• 把已有 Bean 塞进 Filter 执行序

• 不是 new

• 不是反向调用

## 三、你当初“分开”和现在“不拆”并不矛盾

| 阶段 | 做法                               | 目的             |
| ---- | ---------------------------------- | ---------------- |
| 早期 | 想拆链 / 拆配置                    | 防自调用、防循环 |
| 现在 | 单链 + ApplicationContext 名字装配 | 同目的，更轻量   |

👉 动机一致，手段进化

## 四、唯一还值得你留个“心眼”的地方（不是必须）

如果你以后在 `PublicTenantResolver` 里：

• 调了 `ResourceSecurityProperties`

• 调了 resource 模块的 `@Service`

• 而那个 Service 又走了 SecurityContext


那才可能回到你当初担心的自调用。

现在你这套：
• resolver 只做 cache + Feign

• 不碰 Security

✅ 安全
