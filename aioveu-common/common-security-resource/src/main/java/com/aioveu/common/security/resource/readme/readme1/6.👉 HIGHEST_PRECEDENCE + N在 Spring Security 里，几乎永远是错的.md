## 二、你这个常量表的真实含义（你以为 vs 实际）

### ❌ 你以为的顺序（心理模型）

```text
HIGHEST_PRECEDENCE
→ PublicTenant
→ JwtVersion
→ JwtBlacklist
→ Tenant
→ Spring Security 认证
```

### ✅ 实际在 Spring Security 中的顺序（残酷现实）

```text
HIGHEST_PRECEDENCE
→ 你的四个 Filter（全部 ✅）
→ SecurityContextPersistenceFilter
→ BearerTokenAuthenticationFilter   ← JWT 解码发生在这里
→ 后续认证 / 授权
```

👉 你的 Filter 全都在「JWT 还没解码」之前执行

## 三、为什么这是“致命冲突”？（结合你资源服务器配置）

你资源服务器里写的是：

```java
.addFilterBefore(jwtVersionFilter, BearerTokenAuthenticationFilter.class)
.addFilterBefore(jwtBlacklistFilter, BearerTokenAuthenticationFilter.class)
.addFilterBefore(tenantFilter, BearerTokenAuthenticationFilter.class)
```

而你的 order 是：

```java
PUBLIC_TENANT_FILTER  = HIGHEST_PRECEDENCE + 10
JWT_VERSION_FILTER    = HIGHEST_PRECEDENCE + 20
JWT_BLACKLIST_FILTER = HIGHEST_PRECEDENCE + 30
TENANT_FILTER         = HIGHEST_PRECEDENCE + 40
```

### ✅ 结果是什么？

| Filter                            | 执行时机        |
| --------------------------------- | --------------- |
| `PUBLIC_TENANT_FILTER`            | ✅ 最早          |
| `JWT_VERSION_FILTER`              | ✅ 在 JWT 解码前 |
| `JWT_BLACKLIST_FILTER`            | ✅ 在 JWT 解码前 |
| `TENANT_FILTER`                   | ✅ 在 JWT 解码前 |
| `BearerTokenAuthenticationFilter` | ❌ 还没执行      |
| `JwtDecoder.decode()`             | ❌ 还没执行      |

👉 你在“JWT 还没出生”的时候，就去查黑名单、查租户、解析 tenantId

## 四、为什么 `/me` 会“根本没进 Filter”？（关键联动）

因为：

1. `/me` 不在白名单
2. 请求进入
3. `BearerTokenAuthenticationFilter` 尝试解码 JWT
4. JWT 解码阶段直接抛异常
5. Spring 直接返回 500
6. 你的 Filter 根本没机会执行

👉 不是日志没打，是 Filter 没被调用

## 五、Spring Security 官方的 Filter 顺序（你该对齐的）

### ✅ 正确参考区间（非常重要）

| Filter                             | Order                     |
| ---------------------------------- | ------------------------- |
| `SecurityContextPersistenceFilter` | `Integer.MIN_VALUE + 100` |
| `BearerTokenAuthenticationFilter`  | `~ -100`                  |
| `AuthorizationFilter`              | `~ 100`                   |
| 你的 JWT 校验类 Filter             | after BearerToken         |
| 你的 租户 Filter                   | after JWT 校验            |

👉 所有依赖 JWT 的 Filter，必须在 `BearerTokenAuthenticationFilter` 之后

## 六、你现在这个常量表的「正确改法」（生产级）

### ✅✅✅ 推荐方案（最清晰、最安全）

```java
public final class SecurityFilterOrders {

    /**
     * ✅ 公共租户解析（不依赖 JWT）
     * 用于 /public/** 等接口
     */
    public static final int PUBLIC_TENANT_FILTER = Ordered.HIGHEST_PRECEDENCE + 10;

    /**
     * ✅ JWT 解码已经完成
     * 可以安全访问 JwtAuthenticationToken
     */
    public static final int JWT_VERSION_FILTER = 100;

    /**
     * ✅ 校验 JWT 是否被吊销
     * 必须在 JWT 解码后
     */
    public static final int JWT_BLACKLIST_FILTER = 200;

    /**
     * ✅ 从 JWT 解析租户
     * 必须在 JWT + 黑名单之后
     */
    public static final int TENANT_FILTER = 300;

    private SecurityFilterOrders() {}
}
```

### ✅ 然后 SecurityConfig 里必须改成：

```java
.addFilterAfter(jwtVersionFilter, BearerTokenAuthenticationFilter.class)
.addFilterAfter(jwtBlacklistFilter, BearerTokenAuthenticationFilter.class)
.addFilterAfter(tenantFilter, BearerTokenAuthenticationFilter.class)
```

👉 order + addFilterAfter 双重保证

## 七、为什么不能再用 `HIGHEST_PRECEDENCE + N`？

因为：

• `HIGHEST_PRECEDENCE` ≈ `Integer.MIN_VALUE`

• Spring Security 内部 Filter 也在用

• 你永远不知道哪个内部 Filter 会被挤到前面

• 调试极其困难


👉 这是 Spring Security 官方不推荐的写法
