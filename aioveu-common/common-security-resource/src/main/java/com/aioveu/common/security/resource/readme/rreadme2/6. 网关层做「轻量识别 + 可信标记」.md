# 二、为什么「业务层识别」更适合你（逐条拆解）

## ✅ 1️⃣ 你存在「网关无法解析」的场景

你现在已经有：

• clientId → tenantId（需要查）

• Feign 内部调用（无 JWT、无 header）

• 公共接口（非用户态）


这些场景 网关根本不应该、也没能力处理

> ❗如果网关是“主识别器”，这些请求你要么：
> - 不敢放行
> - 要么被迫把逻辑搬到网关

👉 你现在的痛苦，正是因为这个边界被压在网关了

---

## ✅ 2️⃣ 租户解析本质是「业务语义」，不是基础设施

你解析 tenantId 时，隐含了很多业务假设：

• clientId 是否有效

• tenant 是否被禁用

• 是否灰度租户

• 是否特殊内部租户


这些都不是网关该管的

### 网关适合说：

> ✅ “这是 clientId = mall-app”

### 业务层适合说：

> ✅ “mall-app → tenantId = 18，状态正常，允许访问”

👉 你现在的 Filter，干的正是后者

---

## ✅ 3️⃣ 你这套已经在业务层了，而且很完整

你现在已经有：

• ✅ `ClientIdTenantResolutionFilter`

• ✅ `TenantFilter`

• ✅ `TenantContextHolder`

• ✅ Cache + Feign 兜底

• ✅ Filter 仲裁机制


👉 这不是“还没想好放哪”
👉 这是“已经正确放在业务层了”

# 三、那网关层应该干什么？（不是啥都不干）

### ✅ 网关层做「轻量识别 + 可信标记」

我给你一个非常成熟、可落地的网关职责清单：

| 网关做的事              | 说明                  |
| ----------------------- | --------------------- |
| JWT 验签                | ✅ 标准                |
| 从 JWT 提取 `tenant_id` | ✅ 只读                |
| 标记请求来源            | ✅ `X-Client-Verified` |
| 统一 Header 透传        | ✅ Trace / Auth        |
| 路由级租户隔离          | ✅ 物理 / 逻辑集群     |

### ❌ 网关不做的事（你这套）

• ❌ clientId → tenantId 查库

• ❌ 租户状态判断

• ❌ 业务降级逻辑

• ❌ 强制业务服务信任 Header tenantId
