## ✅ 一句话终极答案（先钉死）

> ❌ 不是你代码“退化”了

> ❌ 不是 JWT 坏了

> ✅ 真正原因是：

```text
你现在这个微服务 / 这个依赖组合 / 这个 Spring Boot 版本
↓
Spring Boot 的「自动 JwtDecoder」
↓
不再满足你当前的 JWT（iss / aud / 校验时机）
```

👉 以前能过，是因为“默认校验没被触发”
👉 现在不过，是因为“默认校验被激活了”

## 二、为什么「之前不写 `jwtDecoder` 可以」？

### ✅ 以前能过的真实原因（非常关键）

在 早期 / 某些组合下，Spring Boot 的自动行为是：

```text
有 jwk-set-uri
↓
自动创建 NimbusJwtDecoder
↓
✅ 只验签名 + exp
❌ 不强制校验 iss
❌ 不强制校验 aud
```

前提条件是：

| 条件                                        | 是否满足 |
| ------------------------------------------- | -------- |
| 没自定义 `JwtDecoder`                       | ✅        |
| 没自定义 `SecurityFilterChain` 太细         | ✅        |
| 没启用 `JwtAuthenticationProvider` 二次包装 | ✅        |
| 没加自定义过滤器                            | ✅        |
| Spring Boot / Security 版本较老             | ✅        |

👉 那时候：默认 decoder = “宽松模式”

---

## 三、为什么「现在突然就不行了」？

### ✅ 你现在触发了 **三个致命变化**

---

### ✅ 变化 ①：你**自己定义了 `JwtDecoder` Bean**

```java
@Bean
public JwtDecoder jwtDecoder(OAuth2ResourceServerProperties props) { ... }
```

🚨 一旦你定义了 `JwtDecoder` Bean：

• ❌ Spring Boot 不会再创建“默认宽松 decoder”

• ✅ 你必须自己决定校验规则

• ✅ 否则 Spring Security 会 fallback 到“严格默认校验”


👉 这是最关键的一点

---

### ✅ 变化 ②：你 **没有在 `oauth2ResourceServer` 里显式使用它**

```java
.oauth2ResourceServer(rs -> rs
    .jwt(jwt -> jwt
        .jwtAuthenticationConverter(...)
        // ❌ 没有 .decoder(jwtDecoder)
    )
);
```

结果是：

• ✅ 你有 `JwtDecoder` Bean

• ❌ 但 `JwtAuthenticationProvider` 没用它

• ✅ Spring 重新生成一个“标准校验”的 decoder

• ✅ 标准校验 = iss + aud + exp


👉 你现在的 JWT：

```json
"iss": "http://192.168.1.3:9000"
"aud": "mall-admin"
```

❌ 和 resource server 的默认期望不一致
❌ 直接失败，但不抛明显异常

---

### ✅ 变化 ③：Spring Security 6.x 的默认行为变严格了

在 Spring Security 6+：

| 项目       | 旧版本 | 6.x        |
| ---------- | ------ | ---------- |
| `iss` 校验 | ❌ 可选 | ✅ 默认开启 |
| `aud` 校验 | ❌ 可选 | ✅ 默认开启 |
| 缺失 claim | ❌ 警告 | ✅ 直接失败 |

👉 你这套 JWT 在 5.8 能过，在 6.x 必炸

## 四、为什么你之前“没写 `jwtDecoder` 也能过”？

### ✅ 用一句话还原当时的状态

> 当时：你没定义 `JwtDecoder`
>
> Spring Boot 自动创建了一个“宽松 decoder”
>
> JWT 刚好能过

### ✅ 现在的状态是

> 你现在定义了 `JwtDecoder`
>
> 但没告诉 Spring Security 用它
>
> Spring 改用“严格 decoder”
>
> JWT 被拒

✅ 不是 JWT 变了
✅ 不是 MP 变了
✅ 是 Spring Security 的“默认契约”变了

---

## 五、用一张“因果链”把这件事彻底说清

```text
以前
└─ 没定义 JwtDecoder
   └─ Spring Boot 自动创建宽松 decoder
      └─ 只验签名 + exp
         └─ JWT 通过 ✅

现在
└─ 你定义了 JwtDecoder
   ├─ 但没在 oauth2ResourceServer 中声明使用
   └─ Spring 使用严格默认 decoder
      ├─ 校验 iss ✅
      ├─ 校验 aud ✅
      └─ JWT 不匹配 → 无 Authentication ❌
```

## 六、✅ 你现在的正确做法（二选一）

### ✅✅ 方案一（✅ 强烈推荐，最稳）

显式绑定你自己的 decoder

```java
@Bean
public SecurityFilterChain securityFilterChain(
        HttpSecurity http,
        JwtDecoder jwtDecoder
) throws Exception {

    http
        .oauth2ResourceServer(rs -> rs
            .jwt(jwt -> jwt
                .decoder(jwtDecoder)   // ✅ 生死线
                .jwtAuthenticationConverter(jwtAuthenticationConverter())
            )
        );

    return http.build();
}
```

✅ 这是“契约明确”的做法
✅ 不会再被 Spring 暗箱操作

---

### ✅✅ 方案二（次优，不推荐）

删掉你自己的 `JwtDecoder` Bean

```java
// ❌ 删除整个 jwtDecoder() 方法
```

然后 完全交给 Spring Boot 自动配置

⚠️ 但风险是：
• ✅ 下次升级 Spring Boot 可能再次炸

• ❌ 多微服务一致性无法保证


👉 不适合你这套多租户架构

## 七、为什么 TenantFilter 永远是对的？

因为它只做了一件事：

```java
if (!(authentication instanceof JwtAuthenticationToken)) {
    throw ...
}
```

✅ 它在替 Spring Security 说真话
✅ 它在告诉你：JWT 根本没被认证
