## 三、如果你在 TenantFilter 里用 `JwtSecurityUtils`

比如你改成这样：

```java
@Override
protected void doFilterInternal(...) {

    Long tenantId = JwtSecurityUtils.getTenantId();

    if (tenantId == null) {
        throw new IllegalStateException("Missing tenant_id");
    }

    TenantContextHolder.setTenantId(tenantId);
    filterChain.doFilter(request, response);
}
```

### ✅ 会发生什么？

1️⃣ `JwtSecurityUtils.getTenantId()`  
→ 读 `SecurityContextHolder.getContext().getAuthentication()`  
→ `instanceof JwtAuthenticationToken`  
→ `jwtAuth.getToken()`  
→ `jwt.getClaim("tenant_id")`

👉 和你现在这份代码，最终路径一模一样

### ✅ 在**你当前 Filter 顺序下**：

• ✅ `BearerTokenAuthenticationFilter` 已执行

• ✅ Authentication 已存在

• ✅ JWT 已解析

• ✅ 不会 NPE

• ✅ 不会语义错乱


所以从“能不能跑”的角度：
✅ 完全没问题

## 四、那为什么我不推荐？（架构三刀）

### ✅ 第一刀：**职责错位**

TenantFilter 的定位是：

> “从 Authentication 里把租户信息拿出来，放进线程上下文”

而 `JwtSecurityUtils` 的定位是：

> “给 Service / Controller 用的 JWT 读取工具”

👉 Filter 是基础设施
👉 Utils 是业务代码工具

你在 Filter 里用 Utils：

• ❌ Filter 依赖了“业务工具”

• ❌ 工具类反过来影响基础设施

• ❌ 后期 Utils 一改，Filter 跟着抖


---

### ✅ 第二刀：**语义不诚实**

你现在的代码：

```java
Authentication authentication =
    SecurityContextHolder.getContext().getAuthentication();

if (!(authentication instanceof JwtAuthenticationToken jwtAuth)) {
    throw ...
}

Jwt jwt = jwtAuth.getToken();
Object tenantIdObj = jwt.getClaim(...);
```

👉 这代码在说真话：

> “我只认 `JwtAuthenticationToken`  
> 我只从 Authentication 里拿  
> 没有就不玩”

如果你换成 `JwtSecurityUtils.getTenantId()`：

👉 代码在说谎：

> “我不知道 Authentication 是什么  
> 我只是一个通用工具调用”

但 TenantFilter 明明是最苛刻的那个守卫
不该装成“通用工具人”。

---

### ✅ 第三刀（最关键）：**以后你改认证链，Filter 会炸**

假设有一天你：

• 换成自定义 `AuthenticationToken`

• 接入内部 RPC / client_credentials

• 网关已经解析好 tenantId，直接塞 Authentication


这时候：

• ✅ `JwtSecurityUtils.getTenantId()` → `null`

• ❌ TenantFilter 直接炸

• ❌ 你不得不改 Utils + 改 Filter


而如果你保持现在这份写法：

```java
if (!(authentication instanceof JwtAuthenticationToken jwtAuth)) {
    throw ...
}
```

👉 炸得明明白白
👉 你知道该在哪适配新 Authentication
