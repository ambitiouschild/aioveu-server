> ✅ **有用，但「不是你这套场景的主力」**
>
> ✅ **在你现在的 Security Filter 链里：order 是“备胎”，`addFilterBefore`才是“正房”**
>
> ❌ **如果你只靠 order，90% 会翻车**

## 一、先给结论表（你以后就按这个记）

| 场景                                                       | order 有没有用   | 谁说了算                  |
| ---------------------------------------------------------- | ---------------- | ------------------------- |
| **Servlet 容器 Filter** (`FilterRegistrationBean`)         | ✅ **100% 有用**  | `setOrder()`              |
| **Spring Security 自定义 Filter**                          | ⚠️ **有条件有用** | `addFilterBefore / After` |
| **Spring 内置 Filter** (`BearerTokenAuthenticationFilter`) | ❌ **你改不了**   | Spring 内部               |
| **你现在的 `JwtAuthSkippingFilter`**                       | ⚠️ **几乎没用**   | `addFilterBefore()`       |

------

## 二、为什么你这套里，`order`基本是“摆设”？

### ✅ 关键原因只有一个：

> **Spring Security 的 Filter 链，不是靠 order 排序的**

它是靠这个：

```
http.addFilterBefore(A, B.class);
http.addFilterAfter(C, B.class);
```

👉 **这是“相对顺序”**

👉 **不是“全局数值排序”**

------

## 三、Spring Security 是怎么对待 `Ordered`的？（源码级真相）

你实现了：

```
public class JwtAuthSkippingFilter
        extends OncePerRequestFilter
        implements Ordered {

    @Override
    public int getOrder() {
        return SecurityFilterOrders.JWT_AUTH_SKIPPING; // -205
    }
}
```

### ❌ Spring Security **不会**这样做：

```
把所有 Filter 拿出来
按 order 从小到大排个序
```

### ✅ Spring Security **实际做的是**：

1. 

   把你显式 `addFilterBefore / After`的 Filter

2. 

   **按你声明的相对位置插入**

3. 

   order **只在“同层未指定顺序时”作为 fallback**

👉 **你没指定相对位置，order 才可能起作用**

👉 **你一旦用了 `addFilterBefore()`，order 就被无视了**

------

## 四、那 `order`到底什么时候“真有用”？

### ✅ 情况 1：Servlet 容器 Filter（✅ 你这个用对了）

```
@Bean
public FilterRegistrationBean<PublicTenantFilter> publicTenantFilter() {
    FilterRegistrationBean<PublicTenantFilter> bean = new FilterRegistrationBean<>();
    bean.setOrder(-210);
    return bean;
}
```

✅ **这里 order 是决定性的**

✅ **Tomcat 严格按 order 执行**

👉 **这也是为什么 `PUBLIC_TENANT_FILTER`的 order 是有价值的**

------

### ✅ 情况 2：Spring 自己也没办法确定顺序时（兜底）

比如：

- 

  多个 Filter 都被自动注册

- 

  没有显式 `addFilterBefore`

- 

  Spring 只能按 `Ordered`排序

👉 **这是“保底逻辑”，不是设计逻辑**

------

## 五、为什么你**不能**只靠 order 放 `JwtAuthSkippingFilter`？

### ❌ 原因 1：你控制不了 `BearerTokenAuthenticationFilter`的 order

```
BearerTokenAuthenticationFilter
```

- 

  是 Spring 内置的

- 

  order 是 Spring 内部算的

- 

  **你改不了、也不该改**

👉 **你只能用 `addFilterBefore()`插到它前面**

------

### ❌ 原因 2：order 无法保证跨模块一致性

你现在的 order：

```
JWT_AUTH_SKIPPING = -205;
JWT_AUTH_FILTER   = -200;
```

看起来很美，但：

- 

  Spring 某次升级改了内置 order

- 

  你这个 `-205`突然变成了 **在 JWT 后面**

- 

  401 莫名其妙出现

👉 **这不是理论，是真实踩坑案例**

------

### ❌ 原因 3：order 不表达“意图”

```
order = -205
```

别人看到只能猜：

- 

  这是什么？

- 

  为什么是 -205？

- 

  插在谁前面？

而：

```
addFilterBefore(
    jwtAuthSkippingFilter,
    BearerTokenAuthenticationFilter.class
)
```

👉 **一眼就知道：在 JWT 认证前跳过**

------

## 六、那 `order`在你这套里，**真正的价值是什么？**

✅ **三个价值，而且都很重要：**

### ✅ 1️⃣ 语义锚点（最重要）

```
JWT_AUTH_SKIPPING = -205;
```

👉 **告诉后来人：**

> “在我的认知模型里，JWT 认证从这里开始”

------

### ✅ 2️⃣ 调试友好

日志里看到：

```
JwtAuthSkippingFilter order=-205
```

👉 **你知道它大概在哪个区间**

👉 **出问题能快速定位**

------

### ✅ 3️⃣ 防止“意外重复注册”

如果两个 Filter 都：

- 

  没指定相对顺序

- 

  order 相同

👉 **Spring 至少能给你一个稳定顺序**

## 八、给你一句“面试级总结”（你可以直接用）

> **在 Spring Security 中，Filter 的顺序由 `addFilterBefore / After`决定，而不是 `Ordered`接口。**
