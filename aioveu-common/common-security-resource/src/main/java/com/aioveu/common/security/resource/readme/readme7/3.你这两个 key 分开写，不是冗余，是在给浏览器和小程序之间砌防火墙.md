## 一、先给死刑级结论（人话）

> **如果你 JWT 里同时存在 `userId`（浏览器）和 `memberId`（小程序）两种主体，且二者 ID 空间可能重叠（比如都是自增 1–N），那就——**
>
> ✅ **必须分开写**
>
> ❌ 不能共用一个 key 前缀

如果 ID 空间绝对不重叠（比如 `userId > 1_000_000_000`，`memberId < 1_000_000_000`），理论上能混，但**生产环境不推荐**。

------

## 二、为什么你现在必须分开（对照你自己的模型）

你贴的：

```
String USER_TOKEN_VERSION = "auth:user:token_version:";
String MEMBER_TOKEN_VERSION = "auth:member:token_version:";
```

而你的 JWT 事实是：

- 

  浏览器：`userId = 10`

- 

  小程序：`memberId = 10`

如果你只写：

```
"auth:token_version:10"
```

会发生什么？

| 场景                 | 结果                       |
| -------------------- | -------------------------- |
| 浏览器用户 10 改密码 | 清 `auth:token_version:10` |
| 小程序会员 10 在线   | ❌ 被误踢下线               |
| 小程序会员 10 改信息 | 清同一个 key               |
| 浏览器用户 10 在线   | ❌ 被误踢下线               |

**这就是生产事故。**

## 三、你当前 Filter 的正确配套写法（粘去用）

### 1️⃣ Redis Key 选择逻辑（在 JwtVersionFilter 里）

```
Long userId = ClaimUtils.getClaimAsLong(jwt, JwtClaimConstants.User.ID);

    versionKey = RedisKeyUtils.USER_TOKEN_VERSION + userId;
} else if (memberId != null) {
    versionKey = RedisKeyUtils.MEMBER_TOKEN_VERSION + memberId;

}
```

## 四、什么时候“可以”不分开（供你决策）

| 条件                                     | 能否合并   |
| ---------------------------------------- | ---------- |
| userId / memberId 来自同一张表、同一序列 | ✅ 可以     |
| 浏览器和小程序用户体系彻底打通           | ✅ 可以     |
| 你计划未来做「统一用户中心」             | ✅ 可以     |
| 现在两张表、两个服务、ID 各自自增        | ❌ 必须分开 |

从你之前日志看：

- 

  `ums_member`表

- 

  `memberId=10`

- 

  浏览器端另有 `user`体系

👉 **你现在属于“必须分开”**
