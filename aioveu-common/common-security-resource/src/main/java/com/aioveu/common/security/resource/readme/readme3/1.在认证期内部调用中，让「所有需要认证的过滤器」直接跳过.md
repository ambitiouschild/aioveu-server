## 二、为什么这是主流？（四个不可反驳的理由）

### ✅ 1️⃣ 这是 OAuth2 的「职责边界」决定的

OAuth2 明确区分：

| 阶段           | 是否应该有 JWT |
| -------------- | -------------- |
| 认证前         | ❌ 没有         |
| `/oauth/token` | ❌ 没有         |
| 认证成功后     | ✅ 才有         |

👉 认证期内部调用，本来就不该进入 Resource Server 的认证链

这是 RFC 级别的职责划分，不是 Spring 的特例。

---

### ✅ 2️⃣ Spring Security 官方就是这么教的

Spring Security 里，所有认证端点本身都是“跳过认证过滤器”的：

```java
/oauth/token
/oauth/authorize
/.well-known/openid-configuration
```

源码里到处都是：

```java
shouldNotFilter(request)
```

👉 你做的事，和 Spring 自己做的一模一样

---

### ✅ 3️⃣ 所有主流 OAuth2 产品都这么做

| 产品        | 做法                      |
| ----------- | ------------------------- |
| Keycloak    | 认证服务 / 资源服务分离   |
| Auth0       | Management API 不走 JWT   |
| Azure AD    | Token endpoint 无认证     |
| 阿里 / 蚂蚁 | 认证中心内部 RPC 不走 JWT |

👉 你这个 Feign，就是“认证中心内部 RPC”

---

### ✅ 4️⃣ 多租户 SaaS 里，这是“基础设施通道”的标准模型

你现在这个接口：

```text
/aioveu/api/v8/admin/tenant/users/{username}/{tenantId}/UserAuthCredentials
```

在多租户 SaaS 里，它的标准定位是：

> ✅ 认证基础设施接口
> ✅ 不属于业务 API
> ✅ 不走租户 / JWT 校验

业内一般叫：

• Internal Auth API

• Bootstrap API

• Trusted Backchannel Call


👉 全部都是“跳过认证过滤器”的设计

## 三、那为什么你会怀疑“是不是主流”？

因为你潜意识里有两个非常常见的误解：

✅ 错
跳过认证 ≠ 不校验

你这个接口：
• ✅ 只在 auth 流程中使用

• ✅ 不暴露给外部

• ✅ 不返回业务数据

• ✅ 只用于认证决策


👉 跳过 JWT，是正确裁剪责任边界
