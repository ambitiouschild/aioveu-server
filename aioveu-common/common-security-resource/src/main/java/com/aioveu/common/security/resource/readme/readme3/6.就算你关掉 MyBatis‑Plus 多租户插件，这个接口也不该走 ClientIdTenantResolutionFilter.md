---

## 一、为什么「关了 MP 多租户」也不行？

### ❌ 你现在的推理大概是：

> “我关了 MP 多租户插件  
> SQL 就不会自动拼 `tenant_id`  
> 那我就可以随便走 `ClientIdTenantResolutionFilter` 了”

### ❌ 问题不在 MP，而在**语义和时序**

---

## 二、这个接口的「本质身份」再强调一次

```text
GET /aioveu/api/v8/admin/tenant/users/tenants/{username}
```

### ✅ 它在回答的问题是：

> “这个用户，有哪些租户？”

### ❌ 它回答不了、也不该回答：

> “当前请求属于哪个 tenantId？”

---

## 三、如果你让它走 `ClientIdTenantResolutionFilter`，会发生什么？

### ❌ 逻辑倒置链（非常关键）

```text
1️⃣ 用 clientId 解析出 tenantId
2️⃣ 设置 TenantContextHolder
3️⃣ 查询该用户在该 tenant 下的数据
4️⃣ 返回“单租户结果”
```

👉 结果：
• 用户明明有 3 个租户

• 你只返回了 1 个

• 而且是 clientId 绑定的那个


✅ 这不是“技术问题”
✅ 这是“业务语义错误”

---

## 四、关了 MP 多租户 ≠ 接口语义改变

| 维度                                      | 事实     |
| ----------------------------------------- | -------- |
| MP 是否自动拼 tenant_id                   | ❌ 不拼   |
| SQL 是否需要 tenant_id                    | ❌ 不需要 |
| 接口是否需要 tenantId                     | ❌ 不需要 |
| 是否应该解析 tenantId                     | ❌ 不应该 |
| 是否应该走 ClientIdTenantResolutionFilter | ❌ 不应该 |

👉 关插件只是“不报错”
👉 不等于“这个接口就该有 tenantId”

---

## 五、✅ 正确的判断标准（记住这条）

> 一个接口要不要走 `ClientIdTenantResolutionFilter`，不是看：
>
> ❌ “我能不能关 MP”
>
> ✅ 而是看：这个接口在业务上，是否已经知道自己在哪个租户

### ✅ 适合走 `ClientIdTenantResolutionFilter` 的接口

| 接口                 | 是否适合 |
| -------------------- | -------- |
| 广告分类（租户维度） | ✅        |
| 商品分类（租户维度） | ✅        |
| Banner               | ✅        |
| 首页配置             | ✅        |
| 租户信息查询         | ❌        |
| 用户→租户列表        | ❌        |

---

## 六、✅ 这个接口“正确的一生”

```text
前端输入用户名
↓
调用 /tenants/{username}
↓
不解析 tenantId
↓
查 user_tenant 关系表
↓
返回租户列表
↓
前端选择租户
↓
/oauth/token?tenantId=xxx
↓
✅ 此时才开始有 tenantId
```

👉 tenantId 是“结果”，不是“前提”

---

## 七、一句话把这件事彻底封死

> ❌ 关掉 MyBatis‑Plus 多租户插件，并不能改变“这个接口不该有 tenantId”的事实
>
> ❌ `ClientIdTenantResolutionFilter` 只适合“已经确定租户”的公共请求
>
> ✅ “用户名 → 租户列表”是租户上下文的来源，不是租户解析的消费者

---

## 八、给你一句“架构评审级”总结（可以直接用）

> 在多租户登录体系中：
>
> - 租户解析只能发生在租户上下文确立之后
> - 用户名到租户的映射，是租户上下文的来源，而非其应用场景
> - 任何在尚未确定租户前就解析 tenantId 的行为，都是逻辑倒置，即使技术上可行，也应禁止。
