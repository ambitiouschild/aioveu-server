## 一、先给一句话把认知扶正

> JWT 认证成功 ≠ Token 仍然合法可用

这两个是完全不同的维度：

| 维度         | 谁负责                            | 回答什么问题                                |
| ------------ | --------------------------------- | ------------------------------------------- |
| ✅ JWT 认证   | `BearerTokenAuthenticationFilter` | 这个 JWT 是不是我签的？过期没？结构对不对？ |
| ✅ 版本校验   | `JwtVersionFilter`                | 这个 JWT 对应的账号，是不是已经被强制下线？ |
| ✅ 黑名单校验 | `JwtBlacklistFilter`              | 这个 JWT 是不是被主动注销 / 踢下线？        |

👉 前者是“密码学问题”
👉 后者是“业务安全状态问题”

---

## 二、为什么“已经认证”还要查版本？（这是你系统的刚需）

你这个系统里，版本号解决的是：

> ✅ “我改了用户安全状态，旧 Token 必须全部失效”

### ✅ 典型场景：

• 修改密码

• 管理员踢人

• 更换手机号

• 异常登录风控

• 强制所有设备下线


这些场景有一个共同特点：

> ❌ JWT 仍然是合法的
> ✅ 但你“业务上”不让它用了

而 JWT 本身：

• ❌ 无法主动失效

• ❌ 只能靠过期时间

• ❌ 一旦签发，谁也拦不住


👉 所以你必须用 Redis 版本号来“逻辑作废”它

---

## 三、那为什么“已经认证”还要查黑名单？

黑名单解决的是：

> ✅ “这一次登录会话，是否已经被主动终止”

### ✅ 典型场景：

• 退出登录

• 单点登录踢人

• 设备被盗 / 风控

• 管理员强制下线


这些场景：

• ❌ JWT 仍然合法

• ✅ 但你不想让它再进系统


👉 这是 OAuth2 / OIDC 标准推荐做法
👉 Spring Security 官方文档都建议你这么做

---

## 四、那能不能合并成一个 Filter？（现实问题）

### ✅ 技术上：可以
### ❌ 架构上：不建议

#### ✅ 合并版（简化）：

```java
.addFilterAfter(compositeTokenFilter, BearerTokenAuthenticationFilter.class)
```

里面一次 Redis 请求：

• 查版本

• 查黑名单


✅ 性能更好
✅ 代码更少

#### ❌ 但代价是：

• 职责耦合

• 异常类型不清晰

• 后期扩展困难（比如再加一个“设备绑定校验”）

• 日志 & 审计语义混乱


👉 你这套已经是“企业级多租户 + SSO + 风控”架构
👉 拆开是正确成本

## 五、那为什么你会有这个疑问？（非常合理）

因为你潜意识里默认了一个等式：

> “认证 = 一切 OK”

但现实世界的身份体系是分层的：

```
① 凭证合法（JWT 签名、有效期）
② 会话仍然有效（黑名单）
③ 账户状态仍然允许访问（版本号、冻结、禁用）
④ 当前操作被授权（权限、Scope）
```

👉 Spring Security 只帮你做 ①
👉 ② 和 ③，必须你自己做

---

## 六、给你一个“一秒判断要不要放 Filter”的标准

> 只要这件事，在 JWT 签发之后，仍然可能发生变化
>
> ✅ 就必须放在认证之后
> ✅ 就必须每次请求都检查

| 状态         | 是否变化 | 是否要 Filter |
| ------------ | -------- | ------------- |
| JWT 签名     | ❌ 不变   | ❌             |
| JWT 过期     | ❌ 不变   | ❌             |
| 用户版本号   | ✅ 会变   | ✅             |
| Token 黑名单 | ✅ 会变   | ✅             |
| 用户禁用状态 | ✅ 会变   | ✅             |
| 租户状态     | ✅ 会变   | ✅             |
