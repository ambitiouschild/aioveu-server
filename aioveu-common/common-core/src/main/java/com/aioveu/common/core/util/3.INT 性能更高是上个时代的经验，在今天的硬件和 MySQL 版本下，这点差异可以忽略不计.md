## 先说结论

> OMS 存 INT 的性能优势 ≈ 零。但为了这点"零收益"，你付出的维护成本是实打实的。

---

## 逐个击破你担心的点

### 1️⃣ "INT 查询更快"

| 场景          | INT           | VARCHAR(32)         |
| ------------- | ------------- | ------------------- |
| 等值查询（=） | 极快          | 极快，几乎没差别    |
| 有索引        | B+ 树，4 字节 | B+ 树，最多 32 字节 |
| 实际差异      | —             | 差 纳秒级           |

你的 `payment_method` 列上有索引吗？有。那 VARCHAR(32) 的索引效率跟 INT 差距在 现代硬件上是微秒级，对你一个订单详情查询来说完全感知不到。

真正影响查询性能的： 行数、索引设计、慢 SQL、没加分页。不是列类型。

---

### 2️⃣ "INT 占空间更小"

| 类型        | 存储空间                             |
| ----------- | ------------------------------------ |
| TINYINT     | 1 字节                               |
| INT         | 4 字节                               |
| VARCHAR(32) | 实际长度 + 1~2 字节（通常 5~7 字节） |

差 3 个字节。一张订单表假设 1000 万行：

```
1000万 × 3字节 = 30MB
```

30MB。一张表。在现代数据库里连"毛毛雨"都算不上。你的 `total_amount`、`payment_amount` 这些 DECIMAL 字段一个就占 5~8 字节，也没见你纠结啊 😄

---

### 3️⃣ "PAY 存字符串是为了安全，OMS 存数字是为了性能"

这句话逻辑上自相矛盾：

• 你说 PAY 存字符串是为了安全 → 说明你也认可字符串的可读性 + 不怕枚举顺序变化

• 那 OMS 为什么不需要这个"安全"？OMS 的订单数据就不重要了？


实际上 OMS 的订单数据更重要（核心业务数据），反而更应该存字符串。

## 什么时候 INT 真的有意义？

只有在一种场景下 INT 枚举值得：

> 这个字段是超高基数的热点列，并且参与大量范围查询、聚合计算、分区键。

`payment_method` 显然不是——它是个低基数状态列（就那么几种支付方式），一年也加不了几个新值。

真正适合 INT 的枚举是：性别（0/1）、是否删除（0/1）、状态码（但即便如此，现在业界也越来越多用 VARCHAR）。
