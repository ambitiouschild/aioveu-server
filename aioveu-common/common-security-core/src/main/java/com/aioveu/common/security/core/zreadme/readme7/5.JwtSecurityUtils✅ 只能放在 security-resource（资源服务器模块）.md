## ✅ 一句话封板结论

> **`JwtSecurityUtils`✅ 只能放在 `security-resource`（资源服务器模块）**
>
> ❌ 不能放 auth
>
> ❌ 不能放 common-core
>
> ❌ 不能放业务服务里“随便引”

它不是“通用工具”，它是**资源服务器的专属基础设施**。

------

## 二、为什么它“只能”在 security-resource 里？

### 1️⃣ 它的唯一依赖：`JwtAuthenticationToken`

```
Authentication instanceof JwtAuthenticationToken
```

这个条件：

| 模块                   | 是否成立 |
| ---------------------- | -------- |
| auth（认证服务）       | ❌        |
| 内部服务（Feign 调用） | ❌        |
| resource（资源服务器） | ✅        |

👉 **离开 resource，它就废了**

------

### 2️⃣ 它“读的是 JWT，不是用户对象”

`JwtSecurityUtils`的本质是：

> **JWT → Claim → Java 对象**

而 JWT **只存在于资源服务器**：

- 

  OAuth2 内省？

- 

  JWT 校验？

- 

  网关转发？

✅ 都在 **resource 边界**

------

### 3️⃣ 如果放到 common 里，会被“滥用”

一旦你放到 `common-security-core`：

- 

  有人会在 Auth 里用它 → NPE

- 

  有人会在 Service 里用它 → 逻辑错误

- 

  有人会在 Job / MQ 里用它 → 空指针全家桶

👉 **这是 Spring Security 项目里最常见的“工具类污染”**

------

## 三、✅ 正确的模块划分（标准答案）

```
common-security
├── security-core        ✅ SecurityUtils（Auth 用）
├── security-resource    ✅ JwtSecurityUtils（Resource 用）
└── security-auth        ✅ Auth 服务专用扩展
```

### ✅ security-resource 里只放这些：

```
JwtSecurityUtils
JwtClaimConstants
JwtAuthenticationConverter（可选）
```

### ❌ security-resource 里**绝不放**：

- 

  `SysUserDetails`

- 

  `SecurityUtils`

- 

  `UserDetailsService`

- 

  任何“查库”的代码

------

## 四、✅ 那 Auth 服务用什么？

Auth 服务用你现在的：

```
SecurityUtils
├── getUserId()
├── getUsername()
├── getUser()
└── getRoles()
```

✅ 因为 Auth 里：

```
Authentication
 └── UsernamePasswordAuthenticationToken
     └── principal = SysUserDetails
```

**完全匹配**

------

## 五、✅ 一个“不会踩坑”的使用规则（请你背下来）

> **凡是需要从 `Authentication.principal`强转为 `SysUserDetails`的工具类**
>
> 👉 **只能在 Auth / 内部服务**
>
> **凡是只从 `Jwt`读 claim 的工具类**
>
> 👉 **只能在 security-resource**
