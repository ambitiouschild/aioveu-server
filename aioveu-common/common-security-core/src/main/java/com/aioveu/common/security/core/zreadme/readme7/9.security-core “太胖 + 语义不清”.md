## 五、为什么这个方案是“主流 + 不过度设计”？

### ✅ 优点

| 点          | 说明                                |
| ----------- | ----------------------------------- |
| 边界清晰    | auth 永远不会被 Filter 背刺         |
| 可演进      | 以后加 `TenantStrategy` 不影响 auth |
| 符合 Spring | 自动装配只作用在需要的地方          |
| 易维护      | 新人一看就知道“租户在哪”            |
| 不夸张      | 不是 DDD 过度拆分                   |

### ❌ 不拆的代价

• auth 永远活在“我到底会不会被拖下水”的恐惧里

• security-core 越来越不可控

• 新人上来就敢在 auth 里写租户逻辑

## 七、一个非常重要的“判断标准”

你可以用这一句话来判断要不要独立模块：

> **如果一个功能会因为“被间接依赖”而导致 NPE / 自调用 / 语义污染，  
> 那它就值得独立成一个内核模块。**

`PublicTenantFilter` 完美命中。

## 八、✅ 如果你“暂时不想拆模块”，最低代价方案

### ✅ 在现有 security-core 里做“逻辑隔离”

```text
com.aioveu.common.security
├── core
├── auth
├── tenant        ✅【逻辑子模块】
└── resource
```

并在 `security-tenant` 上加：

```java
@ConditionalOnProperty(
    name = "tenant.resolve.enabled",
    havingValue = "true",
    matchIfMissing = false
)
```

✅ 这是“过渡方案”
✅ 以后拆模块成本低
