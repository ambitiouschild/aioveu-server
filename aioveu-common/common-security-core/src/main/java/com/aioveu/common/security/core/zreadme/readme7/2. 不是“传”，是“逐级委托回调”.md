## 二、真实执行链路（请求视角）

假设是一次 普通 HTTP 请求（非 OAuth2 client_credentials）：

```
HTTP Request
  ↓
【resource】PublicTenantFilter
  ↓ 从 Header / Param 里拿 clientId / tenantId
  ↓
【core】PublicTenantResolver.resolveTenantId()
  ↓ 内部调用 TenantLoader.loadTenantId()
  ↓
【resource】TenantLoader 的实现（FeignTenantLoader）
  ↓
【tenant-api】TenantFeignClient.getTenantIdByClientId()
  ↓
【tenant-service】Controller → Service → DB
  ↓
返回 tenantId
  ↓
PublicTenantResolver 缓存 / 校验
  ↓
PublicTenantFilter 写入 ThreadLocal / MDC
  ↓
Controller / Service 执行业务
```

## 三、各层的“责任边界”（非常重要）

### ✅ `tenant-api`
职责：定义契约

```java
Result<Long> getTenantIdByClientId(String clientId);
```

• ❌ 不关心谁调用

• ✅ 只定义“怎么查租户”

• ✅ 可被 Feign / Mock / Stub 实现


---

### ✅ `common-security-resource`
职责：提供“如何查租户”的能力

```java
@Bean
@Primary
public TenantLoader feignTenantLoader(TenantFeignClient client) {
    return clientId -> client.getTenantIdByClientId(clientId).getData();
}
```

• ✅ 是 TenantLoader 的唯一实现

• ✅ 知道 Feign

• ✅ 知道 Result 的解构

• ❌ 不知道 Filter / Resolver 的细节


---

### ✅ `common-security-core`
职责：定义“租户是谁”的规则

```java
public interface TenantLoader {
    Long loadTenantId(String clientId);
}
```

```java
public class PublicTenantResolver {
    private final TenantLoader loader;

    public Long resolveTenantId(String clientId) {
        return loader.loadTenantId(clientId);
    }
}
```

• ✅ 不依赖 Spring Web

• ✅ 不依赖 Feign

• ✅ 可被 auth / resource / job / MQ 共用

• ✅ 是“平台级规则”


---

### ✅ `common-security-resource`
职责：Web 层拦截

```java
public class PublicTenantFilter extends OncePerRequestFilter {

    private final PublicTenantResolver tenantResolver;

    @Override
    protected void doFilterInternal(...) {
        Long tenantId = tenantResolver.resolveTenantId(clientId);
        TenantContext.set(tenantId);
        try {
            filterChain.doFilter(...);
        } finally {
            TenantContext.clear();
        }
    }
}
```

• ✅ 只做 拦截 + 上下文绑定

• ✅ 不查库

• ✅ 不关心数据来源

## 四、为什么看起来“绕”，其实是“对”的？

### ❌ 错误写法（你没犯）

```java
Filter → Feign → DB
```

问题：
• Filter 依赖 Feign

• Web 层耦合 RPC

• core 无法复用


---

### ✅ 正确写法（你现在这个）

```
Filter → Resolver → Loader → Feign → DB
```

优点：

| 层级     | 好处       |
| -------- | ---------- |
| Filter   | 只管 Web   |
| Resolver | 只管规则   |
| Loader   | 只管数据源 |
| Feign    | 只管 RPC   |

✅ 每一层都能单独换实现
✅ 每一层都能单独测试
✅ auth / resource / job 共用 Resolver

## 五、一个非常关键的“认知升级点”

> ❌ 不是 resource 把 TenantLoader “传”给 core
>
> ✅ 而是 core 定义接口，resource 提供实现
>
> ✅ Spring 在启动时把 Bean 注入进去

也就是：

```java
// core：定义需求
PublicTenantResolver(TenantLoader loader)

// resource：提供能力
@Bean
TenantLoader feignTenantLoader(...)
```

👉 这是 IoC，不是参数传递

## 六、你这个流程的“最终正确表述”

> 1️⃣ `tenant-api` 定义 “怎么查租户”
>
> 2️⃣ `resource` 实现 `TenantLoader`（通过 Feign）
>
> 3️⃣ `core` 的 `PublicTenantResolver` 依赖 TenantLoader
>
> 4️⃣ `resource` 的 `PublicTenantFilter` 调用 Resolver
>
> 5️⃣ Resolver 回调 Loader
>
> 6️⃣ Loader 调用 Feign
>
> 7️⃣ Feign 调用 tenant-service

✅ 这是 Spring 架构教科书级流程
