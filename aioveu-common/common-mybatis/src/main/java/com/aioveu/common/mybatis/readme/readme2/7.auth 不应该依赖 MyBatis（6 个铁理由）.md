## ✅ 一句话结论（先拍板）

> auth 服务的本质：认证 / 签发 Token / 校验权限
>
> ✅ 它只关心 `Authentication`
> ❌ 它不应该关心 `Mapper / Entity / SQL`
>
> MyBatis 是“业务数据访问工具”，不是“身份认证基础设施”

---

## 二、为什么 auth **不应该**依赖 MyBatis（6 个铁理由）

### ✅ 1️⃣ 职责边界清晰（最重要）

| 服务     | 职责                    |
| -------- | ----------------------- |
| auth     | 认证、授权、JWT、OAuth2 |
| user     | 用户 CRUD、密码加密     |
| tenant   | 租户管理                |
| business | 业务数据                |

👉 auth 只做“身份裁决”

---

### ✅ 2️⃣ auth 的存储不一定是 RDBMS

很多成熟 auth 服务：

• 内存用户

• LDAP

• Redis

• Keycloak / OAuth2 Server


👉 强依赖 MyBatis = 锁死存储模型

---

### ✅ 3️⃣ 你现在这套架构已经支持“auth 无 MyBatis”

你刚才已经接受了：

```yaml
mybatis:
  tenant-enabled: false
  data-permission-enabled: false
```

👉 再往前一步：
```xml
<!-- auth 的 pom.xml -->
<!-- 直接不引入 common-mybatis -->
```

✅ 完全合法
✅ 完全干净

---

### ✅ 4️⃣ 避免“循环依赖的最后一块拼图”

如果 auth 依赖 mybatis：

```text
auth
 ↓
mybatis
 ↓
TenantLineHandler
 ↓
TenantContextHolder
 ↓
security-core
 ↓
auth
```

👉 这个环你现在终于可以彻底斩断

---

### ✅ 5️⃣ auth 的性能模型不同

auth：

• 高并发

• 短事务

• 极少字段

• 强缓存


👉 MyBatis + Plugin + Interceptor 反而拖慢

---

### ✅ 6️⃣ Spring Security 官方也是这么干的**

Spring Authorization Server：

• 不依赖 JPA

• 不依赖 MyBatis

• 只依赖 Spring JDBC（可选）


👉 你现在的想法，和 Spring 官方一致

### ✅ auth 的用户查询方式（示例）

#### ✅ 方式一：Spring JDBC（轻量）

```java
@Repository
public class UserRepository {

    private final JdbcTemplate jdbcTemplate;

    public User loadUserByUsername(String username) {
        return jdbcTemplate.queryForObject(
            "SELECT id,password FROM sys_user WHERE username=?",
            (rs, rowNum) -> new User(...),
            username
        );
    }
}
```

👉 比 MyBatis 轻
👉 无插件干扰
