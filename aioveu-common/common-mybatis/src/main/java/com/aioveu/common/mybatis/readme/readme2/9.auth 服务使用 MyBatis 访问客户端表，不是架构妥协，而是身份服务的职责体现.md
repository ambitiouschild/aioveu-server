✅ 这一点完全站得住脚，而且非常“正统”。

我直接给你一个“定性结论 + 架构合法性说明 + 一个必须守住的红线”。

---

## ✅ 一句话结论（先拍板）

> auth 服务里存 `oauth2_client` / `sys_client` 表，用 MyBatis 访问，是 100% 合理的。
>
> ✅ 这不是“业务依赖 MyBatis”
> ✅ 这是“身份基础设施依赖数据访问工具”
>
> 👉 Spring Authorization Server 自己也在干这件事（只是它用的是 JDBC）

---

## 二、为什么你这个理由“非常正当”

### ✅ 1️⃣ OAuth2 Client 是“身份元数据的核心”

`oauth2_client` 表通常包含：

• client_id

• client_secret

• grant_types

• scopes

• redirect_uris

• autoapprove


👉 这些不是业务数据
👉 这些是“认证体系的配置数据”

✅ auth 服务“拥有”这些数据，天经地义

---

### ✅ 2️⃣ Spring Authorization Server 官方也是这么干的**

Spring Authorization Server 内部：

• `RegisteredClientRepository`

• `JdbcRegisteredClientRepository`


👉 底层就是 JDBC
👉 只是它帮你封装了

你用 MyBatis 只是换了个 SQL 映射工具，不是换了 架构角色。

---

### ✅ 3️⃣ auth 的 MyBatis 是“受限使用”，不是“滥用”**

你现在这个用法，本质是：

```text
auth
 ├─ RegisteredClientRepositoryImpl
 │    └─ ClientMapper (MyBatis)
 │         └─ oauth2_client
```

✅ 访问范围可控
✅ 不跨业务域
✅ 不触发租户插件

---

## 三、✅ 你现在这套的“架构合法性模型”

### ✅ 正确的 auth 数据访问边界

| 数据            | 是否允许 MyBatis | 说明           |
| --------------- | ---------------- | -------------- |
| `oauth2_client` | ✅                | 身份认证元数据 |
| `sys_user`      | ✅                | 用户身份       |
| `sys_role`      | ✅                | 授权元数据     |
| `sys_tenant`    | ✅                | 平台级租户定义 |
| 业务表          | ❌                | 不属于 auth    |

👉 只要你不碰“业务表”，架构就没破

---

## 四、⚠️ 但你必须守住的一条“红线”（非常重要）

### ❌ auth 里 **绝对不能** 做的事

```java
// ❌ 错误示例
public class ProductMapper { ... }
public class OrderMapper { ... }
public class PmsMapper { ... }
```

一旦 auth 开始访问业务表：

• auth ↔ 业务服务边界消失

• auth 被迫跟随业务升级

• 循环依赖风险急剧上升


👉 auth 的 MyBatis 只能服务于“身份与访问管理（IAM）”

---

## 五、✅ 一个“最佳实践”建议（强烈推荐）

### ✅ 把 auth 的 Mapper 单独分包

```text
aioveu-auth
├── auth-boot
├── auth-domain
└── auth-infrastructure
    └── mapper
        ├── OAuth2ClientMapper
        ├── UserMapper
        └── TenantMapper
```

并在模块层面限制：

> 只有 `auth-infrastructure` 可以依赖 MyBatis

👉 编译期防止 Mapper 泄露
