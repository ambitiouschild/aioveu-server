## 一、IoC 是什么（Inversion of Control，控制反转）

### ✅ 一句话人话版

> 原来你控制流程，现在容器控制流程。

---

### ❌ 没有 IoC（你自己控制一切）

```java
public class OrderService {
    public void createOrder() {
        DataPermissionHandler handler = new MyDataPermissionHandler();
        handler.check();
        // 创建订单
    }
}
```

👉 你：
• new 谁

• 什么时候调用

• 调用几次

• 失败了怎么办


你掌控一切

---

### ✅ 有 IoC（Spring 掌控流程）

```java
@Component
public class OrderService {

    private final DataPermissionHandler handler;

    public OrderService(DataPermissionHandler handler) {
        this.handler = handler;
    }
}
```

👉 你：
• 只声明“我需要一个能力”

• 不决定谁来

• 不决定什么时候调用


👉 Spring：
• 创建 Bean

• 注入依赖

• 决定调用顺序


✅ 控制反转了

---

### ✅ 你刚才的感受，就是 IoC

> “我在 resource 注册了 Bean，MyBatis 自动用上了”

👉 你没有调用 MyBatis  
👉 MyBatis 也没有调用你  
👉 Spring 在中间“反转了控制权

---

## 二、DIP 是什么（Dependency Inversion Principle，依赖倒置）

### ✅ 一句话人话版

> 高层模块不依赖低层模块，大家一起依赖“抽象”。

---

### ❌ 没有 DIP（直接依赖实现）

```java
// common-mybatis
import com.aioveu.security.resource.MyDataPermissionHandler;

public class MybatisPlusConfig {
    private MyDataPermissionHandler handler;
}
```

👉 问题：
• mybatis 依赖 resource

• resource 一改，mybatis 跟着炸

• 模块关系死死的


---

### ✅ 有 DIP（依赖接口）

```java
// common-mybatis
import com.baomidou.mybatisplus.extension.plugins.handler.DataPermissionHandler;

public class MybatisPlusConfig {
    private DataPermissionHandler handler;
}
```

```java
// security-resource
public class MyDataPermissionHandler implements DataPermissionHandler {
}
```

👉 关键点：
• `common-mybatis` 不知道 resource

• 两个模块都只依赖 `DataPermissionHandler`

• 谁实现，无所谓


✅ 依赖“倒过来”了

---

### ✅ 你刚才的设计，就是 DIP

| 模块              | 依赖                            |
| ----------------- | ------------------------------- |
| common-mybatis    | `DataPermissionHandler`（抽象） |
| security-resource | `DataPermissionHandler`（抽象） |
| 实现              | `MyDataPermissionHandler`       |

👉 高层（mybatis）不依赖低层（resource）
👉 大家都依赖接口

---

## 三、IoC 和 DIP 的关系（很多人搞混）

### ✅ 一句话区分

> DIP 是“设计原则”
>
> IoC 是“实现手段”

| 概念           | 本质                            |
| -------------- | ------------------------------- |
| DIP            | 思想：面向接口编程              |
| IoC            | 手段：把控制权交给容器          |
| DI（依赖注入） | 具体实现方式（构造器 / setter） |

---

### ✅ 一个“连环画式”理解

1️⃣ DIP 说：
> “你别依赖我，咱俩都依赖接口。”

2️⃣ IoC 说：
> “那谁来控制流程？”
> “我来。”

3️⃣ Spring 说：
> “我负责创建 Bean、注入依赖、回调你。”

👉 你刚才那句：
> “注册和回调真好用”

就是 DIP + IoC + Spring DI 的三重叠加 😄

## 四、用你自己的代码“对号入座”

### ✅ IoC

```java
@Bean
public DataPermissionHandler dataPermissionHandler() {
    return new MyDataPermissionHandler();
}
```

👉 你把对象“交出去”了

---

### ✅ DIP

```java
Optional<DataPermissionHandler> dataPermissionHandler
```

👉 你依赖接口，不依赖实现

---

### ✅ 两者结合

```java
if (dataPermissionHandler.isPresent()) {
    new DataPermissionInterceptor(dataPermissionHandler.get());
}
```

👉 容器控制流程
👉 模块依赖抽象

## 五、一个“灵魂比喻”（记住这个）

### 🔧 IoC = 外包项目经理

• 以前：你亲自拧螺丝

• 现在：你说“我要一把螺丝刀”，项目经理给你一把

• 你不管螺丝刀怎么造的


---

### 🏗️ DIP = 插座标准

• 插座（接口）定了

• 电视、冰箱、充电器（实现）随便插

• 电视不认识冰箱
