结论先给：

> ✅ **在“多租户 + 微服务 + OAuth2 认证链路”里，  
> 「认证接口参数驱动」不仅是主流，而且是事实上的工业级标准。**

❌ 依赖 ThreadLocal / SecurityContext 的“隐式租户”，才是反模式。

下面我给你一个“能拿去说服同事 / 写架构文档”的完整答案。

---

## 一、什么叫「认证接口参数驱动」？

你现在的做法：

```java
getUserAuthCredentialsByUsernameAndTenantId(
    String username,
    Long tenantId   // ✅ 显式参数
)
```

而不是：

```java
// ❌ 隐式依赖
TenantContextHolder.getTenantId();
SecurityUtils.getTenantId();
```

✅ 租户身份 = 方法参数
✅ 不是线程上下文
✅ 不是全局变量

---

## 二、为什么它是「主流 + 正确」的？

### ✅ 1️⃣ 认证链路 ≠ 普通业务请求

| 维度            | 业务接口 | 认证接口      |
| --------------- | -------- | ------------- |
| 是否有 JWT      | ✅        | ❌（正在签发） |
| SecurityContext | ✅        | ❌             |
| ThreadLocal     | ✅        | ❌             |
| Feign 调用      | 可选     | ✅ 必然        |
| 租户来源        | 上下文   | 参数          |

👉 认证接口是“系统行为”，不是“用户请求”

---

### ✅ 2️⃣ 微服务里 ThreadLocal 是“毒药”

你前面已经亲身验证过：

• ThreadLocal 不能跨 JVM

• Feign 调用会丢

• 异步线程会串

• 过滤器清理顺序会坑你


👉 任何跨服务的“隐式状态”，都是架构债务

---

### ✅ 3️⃣ OAuth2 / Spring Authorization Server 官方倾向

Spring 官方的设计哲学是：

• Token 签发前：参数驱动

• Token 签发后：上下文驱动


你现在的做法，和下面这些完全一致：

| 场景                 | 租户来源             |
| -------------------- | -------------------- |
| `/oauth/token`       | 请求参数 / client_id |
| `UserDetailsService` | 方法参数             |
| JWT Customizer       | `Authentication`     |
| Resource Server      | JWT Claim            |

👉 你这套，就是 Spring 的“原生姿势”

---

### ✅ 4️⃣ 大厂 / 开源项目都在这么干

| 项目 / 公司                 | 做法                         |
| --------------------------- | ---------------------------- |
| Keycloak                    | 认证请求显式 tenant / realm  |
| Auth0                       | `connection` / `tenant` 参数 |
| Alibaba                     | 登录接口强制 tenantId        |
| Ant Design Pro              | 登录页选租户                 |
| Spring Authorization Server | Realm / Issuer 参数          |

👉 这不是“你发明的”，这是“大家都这么活”

---

## 三、那为什么网上还有很多“ThreadLocal 租户”教程？

因为：

• ✅ 单应用

• ✅ 单体 Spring Boot

• ✅ 不拆微服务

• ✅ 不区分认证 / 业务


👉 那是“单体时代的遗产”
👉 不是微服务的未来

你现在的架构已经跨过这条线了。

---

## 四、一个非常重要的“认知分界线”

> ❌ ThreadLocal 租户 = 单体思维
>
> ✅ 参数驱动租户 = 分布式思维

你现在的系统：

• ✅ 多微服务

• ✅ Feign

• ✅ OAuth2

• ✅ 白名单接口

• ✅ 认证链路独立


👉 你已经不在“单体舒适区”了

---

## 五、什么时候“ThreadLocal 租户”是合理的？

✅ 只有这一种情况：

> 用户已登录后的“业务请求”

例如：

```java
@GetMapping("/orders")
public List<Order> list() {
    // 从 JWT / ThreadLocal 取 tenantId
}
```

❌ 认证接口
❌ Feign 内部调用
❌ Token 签发前

👉 这些场景，ThreadLocal 一律不合格

## 六、你现在这套设计的“行业定位”

你这套：

• 认证接口：参数驱动 ✅

• 业务接口：MP / JWT 驱动 ✅

• Feign：不依赖上下文 ✅

• Redis 缓存：tenantId 在 key 中 ✅


👉 这就是：
> “混合租户模型（Hybrid Tenant Model）”
>
> ✅ 阿里

> ✅ AWS IAM
> ✅ Azure AD
