## 一、为什么“手动 set 进 MP”是个坏主意（非常关键）

### 1️⃣ 时机已经晚了（这是硬伤）

你现在的代码执行顺序是：

```
baseMapper.getAuthInfoByUsernameAndTenantId()
  ↓
MP TenantLineHandler 已经执行完毕
  ↓
SQL 已经生成
  ↓
你才在 Service 里 setTenantId()
```

👉 **MP 插件只在 SQL 执行前生效一次**

👉 **Service 里 set 对刚才那条 SQL 毫无影响**

你日志已经证明了这一点：

```
MyTenantLineHandler → TenantContextHolder: null
==> Preparing: SELECT ...
==> Parameters: xinhuan, 3
```

**SQL 早就拼完了，你再 set 等于马后炮。**

------

### 2️⃣ 如果你“提前 set”，会污染整个请求线程

假设你在 Controller / Service 里这么写：

```
TenantContextHolder.setTenantId(tenantId);
try {
    return baseMapper.getAuthInfoByUsernameAndTenantId(username, tenantId);
} finally {
    TenantContextHolder.clear();
}
```

#### 会引发的问题：

| 问题                            | 原因                          |
| ------------------------------- | ----------------------------- |
| MP 自动给**所有表**拼 tenant_id | 包括 sys_role / sys_user_role |
| 忽略表被强制拼 tenant_id        | 变成 `= NULL`                 |
| 角色 / 权限再次查不到           | 你之前踩过的坑                |
| 异步线程 / CompletableFuture    | 租户 ID 泄漏                  |
| Feign 串行调用                  | 串租户                        |

👉 **你不是在“补坑”，是在“挖更大的坑”**

### ② Mapper XML：**100% 手写 tenant_id**

```
<select id="getAuthInfoByUsernameAndTenantId" resultMap="authCredentialsMap">
    SELECT
        t1.id userId,
        t1.username,
        t1.password,
        t1.status,
        t1.dept_id,
        t1.tenant_id,
        t3.code AS role_code
    FROM sys_user t1
    LEFT JOIN sys_user_role t2 ON t2.user_id = t1.id
    LEFT JOIN sys_role t3 ON t3.id = t2.role_id
    WHERE t1.username = #{username}
      AND t1.tenant_id = #{tenantId}
      AND t1.is_deleted = 0
</select>
```

✅ **不依赖 MP**
