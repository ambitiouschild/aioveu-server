能用，但你现在这个 `RolePermsBO` 用在这里“不合适”，而且会让你后面踩一个很隐蔽的坑。  
我直接给你一个“能 / 不能用”的清晰边界，不绕。

---

## ✅ 一句话结论

> ✅ `RolePermsBO` 可以用
>
> ❌ 但不能直接用在 `@MapKey + collection` 的场景里
>
> ✅ 它更适合“单条记录映射”
>
> ❌ 不适合“按 roleCode 聚合成 Map<roleCode, Set<perm>>”

你现在这个 XML：

```xml
<resultMap id="RolePermMap" type="java.util.HashMap">
```

👉 你其实已经在“回避”这个问题了
👉 但还没回避干净

## 二、为什么你现在这个 `RolePermsBO` 用在这里会有坑？

### 1️⃣ MyBatis 的 `@MapKey` 工作机制

当你写：

```java
@MapKey("roleCode")
Map<String, Set<String>> listRolePermsGroupByRoleWithTenantId(...)
```

MyBatis 做的是：

• 每一行 → 映射成一个 `RolePermsBO`

• 用 `roleCode` 当 key

• 把同一个 roleCode 的多行，合并成一个 BO


### 2️⃣ 但 `Set<String> perms` 的合并规则不明确

你的 BO：

```java
private Set<String> perms;
```

问题来了：

• MyBatis 不会帮你 merge Set

• 每一行都会创建一个 `RolePermsBO`

• 后面的行会 覆盖前面的

• 或者只保留最后一条 perm


👉 最终你得到的 Set 可能只有 1 个元素

---

## 三、你这个 `RolePermsBO` 原本是为哪种 SQL 设计的？

看这个 resultMap：

```xml
<resultMap id="PremRolesMap" type="RolePermsBO">
    <id property="tenantId" column="tenant_id"/>
    <id property="roleCode" column="role_code"/>
    <collection property="perms" ofType="string" javaType="java.util.Set">
        <result column="perm"/>
    </collection>
</resultMap>
```

✅ 这个 resultMap 是为“单条记录 → 一个 BO”设计的

而且它配合的是：

```sql
SELECT tenant_id, role_code, perm
FROM ...
```

👉 一行一个 perm
👉 MyBatis 用 `collection` 帮你聚合成 Set

✅ 这是对的
✅ 这个 BO 用在这里是合适的

---

## 四、为什么它不适合 `listRolePermsGroupByRoleWithTenantId`？

因为你现在的 SQL：

```sql
SELECT t3.code AS roleCode, t2.perm AS perm
```

👉 没有 `tenantId`
👉 你在认证接口里已经不依赖 tenantId
👉 但 BO 里还有 `tenantId` 字段

更严重的是：

• `@MapKey("roleCode")`

• `type=RolePermsBO`

• MyBatis 会尝试：

  • 每行 new 一个 BO

  • 塞一个 perm

  • 丢进 Map


👉 Set 聚合行为不可控
👉 调试极其困难

---

## 五、✅ 正确做法（三选一，推荐第 1 种）

---

### ✅✅✅ 方案 1（最推荐）：新建一个“认证专用 BO”

```java
@Data
public class AuthRolePermBO {
    private String roleCode;
    private Set<String> perms = new HashSet<>();
}
```

```xml
<resultMap id="RolePermMap" type="AuthRolePermBO">
    <id property="roleCode" column="roleCode"/>
    <collection property="perms"
                ofType="java.lang.String"
                javaType="java.util.HashSet">
        <result column="perm"/>
    </collection>
</resultMap>
```

✅ 语义清晰
✅ 和认证链路强绑定
✅ 不污染业务 BO

---

### ✅ 方案 2：直接用 `HashMap`（你现在的写法）

```xml
<resultMap id="RolePermMap" type="java.util.HashMap">
```

✅ MyBatis 内部处理最稳定
❌ 无类型约束
❌ 维护成本高

👉 可以用，但不优雅

---

### ⚠️ 方案 3：强行用 `RolePermsBO`（不推荐）

```xml
<resultMap id="RolePermMap" type="RolePermsBO">
```

❌ `tenantId` 没意义
❌ Set 聚合不可控
❌ 后期调试地狱

👉 不建议

## 六、一个非常重要的“认知升级”

> ❌ BO ≠ 任何场景通用
>
> ✅ BO 是“语义 + 使用场景”绑定的
>
> ✅ 认证链路的 BO ≠ 业务查询的 BO

你现在这个 `RolePermsBO`：

• ✅ 适合：`getRolePermsList`

• ❌ 不适合：`listRolePermsGroupByRoleWithTenantId`

## 七、给你一句“架构级判断标准”

> 当一个 BO 里有字段在 SQL 里不存在时，它就不适合这个 SQL。

你这个 `tenantId`：
• XML 里没有

• SQL 里没有

• 认证接口里不需要

• 但 BO 里有


👉 这就是“气味”

>
> ❌ 但用在这个 `@MapKey + group by roleCode` 的场景是错误的
>
> ✅ 正确做法是：新建一个 AuthRolePermBO
>
> ✅ 或者接受 HashMap（次优）
>
> ❌ 不要强行复用 RolePermsBO
